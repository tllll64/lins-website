# Information hierarchy

**Covers:** 用视觉表达已确认的任务信息，包括主次、关系、呈现形式和阅读顺序。

**Use when:** 新建或重组页面；信息主次、关系、呈现形式或阅读顺序不清；视觉元素开始争抢注意力时。

**Does not cover:** 空间、滚动和响应式查 `layout.md`；界面状态和反馈查 `states.md`；颜色查 `color.md`；组件内部样式查组件文档。图表类型与配置、营销场景和展示型排版不在本文维护。

## 先明确任务

### Don't

- 不把页面类型当成完整任务。“做一个 Dashboard”还要说明用户需要查看、比较或操作什么。
- 不照搬业务字段、接口返回顺序或现有组件来安排页面；页面主次按用户任务确定。
- 产品内容未经确认时，不擅自新增、改写或删除。

### 设计原则

先从已确认的产品事实里回答：**谁在什么场景下，要对什么对象完成什么任务。** 无法确认的内容标为待确认。

同类任务优先沿用产品现有的信息结构和交互模式；只有任务目标或约束不同，才重新设计。

再判断信息在任务中的作用：

| 作用     | 判断问题                                         |
| -------- | ------------------------------------------------ |
| 任务     | 用户在处理什么对象，要完成什么动作               |
| 工作     | 完成任务必须查看、输入、选择或比较什么           |
| 支持     | 哪些说明、示例、限制、来源或帮助会影响理解与操作 |
| 元数据   | 哪些时间、创建者或标识符只用于补充               |
| 系统信息 | 哪些进度、错误、权限或同步状态会改变下一步       |

任务决定信息主次。视觉只负责把已确认的主次表达清楚。

## 突出重点

### Do

- 优先级确认后，同级信息使用一致的视觉权重；主要动作与关键结果明显高于辅助信息。
- 已确认必须同时决策且后果对等的动作作为一组呈现。
- 眯眼查看页面时，仍能看出当前任务的重点和主要操作。

### Don't

- 不在界面显示“任务级、工作级、支持级、元数据级”等内部分类名。
- 不让辅助动作、装饰或低影响状态与主要操作争抢注意力。
- 没有产品依据时，不用字号、面积或颜色制造优先级。

### 设计原则

按信息对当前任务的作用判断权重：

| 层级     | 包含内容                         |
| -------- | -------------------------------- |
| 任务级   | 页面目标、关键结果、主要动作     |
| 工作级   | 主体内容、输入、比较和选择       |
| 支持级   | 解释、范围、辅助动作和次要导航   |
| 元数据级 | 时间、ID、来源和不影响操作的状态 |

首次使用、日常操作和失败恢复的重点可以不同。时间和状态不必固定为元数据；是否阻塞任务、后果大小和恢复成本决定其层级。可见状态和反馈样式查 `states.md`，恢复流程由产品 Spec 定义。

## 表达内容关系

### Do

- 分组确认后，先用标题、顺序、邻近、对齐和留白表达关系；仍不清楚时再加背景或边框。
- 已确认的原因与结果、控件与反馈放在一起。错误与恢复动作均已确认时，也放在一起。
- 字段名、必填标记和影响填写方式的约束持续可见；placeholder 只放格式示例。
- 去掉卡片背景、边框和图标后，标题、顺序和邻近关系仍能说明分组。

### Don't

- 不用卡片嵌套代替分组判断。
- 不把完成任务所需的信息藏在 tooltip 或多层折叠中。
- 不添加产品未确认的恢复操作。

### 设计原则

需要一起判断、操作、比较或阅读的内容，通常归为一组。组件相同、接口相同或样式相似，不是分组依据。

不同任务阶段或作用范围的内容应拆开；次要信息开始遮挡主要判断时，也应拆开。低频说明和进阶设置可以按需展开，但不能影响当前判断。

具体间距和容器写法查 `layout.md`。

## 选择呈现形式

### Do

- 指标只显示已确认的信息，并提供判断所需的定义、分母、范围、时间区间、参照值和来源。
- 日期、数字、货币和单位沿用产品既有格式。
- 图标、图像或图表承载业务信息时，同时提供文字或数值，让用户不依赖视觉也能获得同一信息。
- 图表保留已确认的明细路径；路径未确认时标为待确认，不新增页面或跳转。组件和 API 查 `components.md` 的 `components/chart-pro.md`。

### Don't

- 不为迁就现有组件改变信息结构。
- 格式未确认时，不按开发者所在地区猜测。

### 设计原则

先看用户要回答的问题，再选最简单且不丢信息的形式：

- 解释含义、条件或结论，用文字。
- 单一数值足以支持判断时，直接呈现数值。
- 逐项浏览或操作对象，用列表；按相同字段比较多个对象，用表格。
- 识别趋势、分布、比例或变量关系，用图表。

图表类型不在本包维护。

## 安排阅读与操作顺序

### Do

- 同一对象和动作使用同一术语；多视图流程明确入口、去向和返回路径。
- 确认任务顺序后，记录各区域的先后关系；视觉、DOM 和焦点的重排查 `layout.md`。筛选、选择和滚动位置是否保留，由产品或组件契约定义。
- 页面跳转使用链接。
- 链接文案直接说明去向；文案引用某项设置时，直接链接到该设置。
- 按钮写明动作，必要时带上对象，并与实际结果一致。
- 只看标题、主要内容和操作时，仍能回答“在哪里、重点是什么、下一步做什么”。

### Don't

- 单层页面不增加面包屑。
- 需要同时比较的内容不要分散到不同 Tabs。
- 不使用“点击这里”或无上下文的“了解更多”；能直接链接到设置时，不用文字复述多级路径。
- 需要用户判断结果或后果时，不用“确定”“提交”“OK”等泛化文案。

### 设计原则

全局导航表示产品区域，局部导航或 Tabs 表示对象视图，按钮表示动作。Tabs 只适合彼此独立、无需同时查看的视图。

阅读顺序先帮助用户定位，再理解变化和当前任务，最后看到下一步与补充信息。具体顺序由任务决定，不把它当成固定页面模板。

## 用字号、图标和阴影强化层级

### Do

文字角色确认后，使用 Tailwind v3 标准刻度：

| 角色           | 常用起点                               |
| -------------- | -------------------------------------- |
| 页面或流程标题 | `text-xl` / `text-2xl`，`font-medium`  |
| 区域标题       | `text-base` / `text-lg`，`font-medium` |
| 正文与控件     | `text-sm`，沿用组件默认字重            |
| 标签与辅助信息 | `text-xs` / `text-sm`                  |
| 关键数据       | 确认为判断核心后，提高一档字号或字重   |

- 优先使用组件已有的图标插槽。自定义单色功能图标使用 `currentColor`。
- 纯图标按钮提供可访问名称；装饰图标使用 `aria-hidden="true"`。
- 同组图标沿用同一组件或图标库的尺寸和线宽。
- 阴影只用于覆盖页面内容、需要区分前后层级的浮层。
- 用真实多行内容检查文字是否裁切、行高是否可读。

### Don't

- 不在页面写字号裸像素值，也不覆盖组件内部字体族和行高。
- 不给单色功能图标写 hex，不在页面逐个微调图标尺寸和线宽。
- 不给普通卡片、Button、Input 或 hover 状态追加装饰性阴影。
- 不在页面层覆盖组件约定的阴影值和 z-index。
- 交付视觉稿或可运行原型时，不用 emoji、文本字符、CSS 图形或临时占位冒充产品图标、Logo、插画或业务图片；缺少合适资产时标记缺口。

### 设计原则

字号、图标和阴影只能强化已经确认的层级，不能替代优先级判断。层级未确认时，沿用组件默认视觉并标为待确认。

行高随文字角色和实际行数调整：短标题可以紧凑，多行正文和说明优先保证连续阅读。

图标能否单独使用，取决于目标用户是否熟悉其含义，以及误解是否会影响任务；含义不明确时显示文字。
