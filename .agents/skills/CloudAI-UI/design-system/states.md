# Interface states

**Covers:** 定义 Prototype 需要展示的界面状态，以及各状态使用什么内容、组件和视觉反馈。

**Use when:** 设计 loading、empty、error、success、权限、选择、控件状态或反馈样式时。

**Does not cover:** 数据和系统行为由产品或工程 Spec 定义；颜色查 `color.md`；过渡查 `motion.md`；组件 class、props、ARIA 和键盘行为查组件契约。

## 确定需要展示的状态

### Do

- 只展示需求明确要求，且有可见差异的状态。
- 需求未说明的状态不补充；需要演示时使用模拟数据和本地交互。
- 明确状态的影响范围，局部出现 loading、error 或权限限制时，只细化对应区域。

### Don't

- 不为凑齐状态清单，设计没有界面差异的组合。
- 不根据组件名称、颜色或技术术语补充产品状态。
- 任务失败、影响严重和无权限是三件事，不用一个状态同时表达。

### 设计原则

Prototype 只表达需求已确认的界面状态，不设计真实的数据或系统行为。

| 类型 | 按需展示的常见状态                                                      |
| ---- | ----------------------------------------------------------------------- |
| 内容 | initial、loading、content、empty、partial、error                        |
| 操作 | idle、submitting、success、failed                                       |
| 控件 | default、hover、focus、pressed、selected、disabled、expanded、collapsed |
| 访问 | allowed、read-only、permission denied、blocked                          |
| 选择 | none selected、some selected、all selected                              |

## 处理加载、空、错误和受限内容

### Do

- loading 使用“保存中”“正在生成”等具体文字。结构稳定时使用 Skeleton；局部更新时只在对应区域显示进度。
- loading、empty、error 和 content 切换时保持页面结构稳定。
- 首次空态说明能做什么；需求已定义创建入口时再展示。
- 无结果空态保留搜索或筛选条件；需求已定义调整入口时再展示。
- 只有部分内容返回时，继续显示已返回的内容，并明确标出哪些内容缺失。
- 权限或前置条件受限时，说明限制；需求已定义可用操作或返回方式时再展示。
- 错误提示说明发生了什么和影响什么；需求已定义恢复方式时再展示。字段错误提示紧邻字段，区域错误提示留在区域；只有整页不可用时才使用整页错误。

### Don't

- loading 尚未结束时不闪出 empty，也不把不同空态统一写成“暂无数据”。
- 不把权限限制伪装成空数据，不把输入无效当成执行失败。
- 不伪造未确认的技术原因。
- 错误文案不归咎用户。
- 后续仍需查看的说明和帮助不能只出现在首次空态。

### 设计原则

反馈只覆盖受影响范围。

权限、前置条件和错误状态不能混用：无权限说明谁不能做；前置条件说明还缺什么；错误说明当前任务没有完成。

## 表现操作与控件状态

### Do

- default 状态就让入口可识别，hover 只补充反馈。
- focus 保持可见；pressed 在按下时出现；selected 表示已选择；disabled 表示当前不可操作。
- loading 时保持控件尺寸稳定，并沿用组件的 loading 样式。
- 需求明确操作结果时，分别展示 success 或 failed；结果未定义时不在界面补画，在交付说明中标为待确认。
- 需求已明确操作会删除已有数据或版本、撤销权限时，使用组件的 `destructive` 样式。

### Don't

- 不用 hover 作为唯一入口或唯一状态反馈。
- 不移除 focus outline 后又不提供替代表达。
- 不用 disabled 掩盖权限或校验问题。
- 不显示需求没有定义的百分比、剩余时间、取消或完成状态。
- 不因为按钮写着“删除”或“覆盖”就自动使用 `destructive`。

### 设计原则

控件状态表达当前可见的交互结果，不承担产品逻辑。组件已有状态样式时直接沿用，不在页面重复设计。

`destructive` 由需求已确认的操作后果决定，不由文案或颜色反推。

## 选择反馈组件

### Do

- 需要展示无需操作的紧凑状态时，使用 `StatusBadge`。
- 字段问题用字段旁提示；区域问题用 `MessageBar` 或持续可见的 Banner。
- 无需决策的完成结果用 Toast；需要用户确认后果时用 Dialog。

### Don't

- 不在业务页面手拼状态 pill 的文字、背景、描边、图标和尺寸。
- 需要复制、比较或持续处理的问题不能只放 Toast；已发生且无需选择的结果不用 Dialog。
- 需要解释、恢复动作或在区域内持续显示反馈时，不用 StatusBadge 代替 `MessageBar` 或 Banner。

### 设计原则

反馈组件由影响范围、持续时间和是否需要用户决策决定。

## 交付并验证状态样式

### Do

- 只交付当前 Prototype 需要演示的状态；用本地交互或演示开关切换。
- 原型数据和演示状态明确标为模拟，不伪装成真实产品能力。

交付前检查：

- 需求涉及的 loading、empty、error、success 是否都能单独查看；
- 需求涉及的控件状态是否可区分；
- 状态变化时布局和控件尺寸是否稳定；
- 反馈是否限制在受影响区域；
- 文案、组件和颜色是否与状态含义一致。

### Don't

- 不把所有状态组合画成独立页面。
- 不为演示样式补写产品逻辑。
