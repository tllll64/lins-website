# CloudAI Design Spec Generator

把业务目标、PRD、研究材料、数据或现有页面整理成可直接指导 UI 实现与评审的 `design-spec.md`。

## 产物

最终产物是 `design-spec.md`。写入并用 IDE 原生能力打开文件后停止，等待用户确认；本阶段不生成 HTML。

写作前读取 `design-spec-generator/design-spec-template.md`。它是唯一模板真源；最终产物固定使用模板里那六节，不另建第二套结构。

## 信息来源

先确认本次可用的信息来源：用户描述、PRD、研究、数据、现有 Spec、页面、代码、设计稿和设计系统。区分事实、已确认决策、证据、假设与参考材料；有冲突、过期或关键缺口时才提问。

如果项目已有 bmad-method、OpenSpec、spec-kit 或自有 SDD，把其中已确认的内容作为信息来源，不改写其 schema，也不把它当成本次最终产物。仍统一生成 `design-spec.md`。

没有数据时不编造数据或指标值。只有证据会改变结构、排序、分支或行动时，才把它写入 Spec。

## CloudAI 约束

按当前问题读取：

- `design-system.md`：hierarchy、layout、states、color；
- `components.md`：组件选型与契约；
- 当前 brand 的 `design-tokens.json`：准确 token 事实。

Spec 可以把当前任务映射到已有组件、Tailwind 档位和语义 token，但不定义新的 brand 值。禁止裸 hex、裸 px 和任意值；找不到对应组件或 token 时标记“待设计师确认”，不要发明。

Agent、Dashboard 默认不推荐技术栈。用户已提供的技术条件只记录为实现约束；仅用户明确要求技术方案时才补充。

## 写作规则

1. 先确定目标、范围、产品形态、运行容器和端侧，再写信息架构。
2. 先说明信息主次、分组和阅读顺序，再定义空间关系、滚动归属与响应式重排。
3. 每个模块必须归属具体页面或状态，并有进入、返回或完成路径。
4. 组件优先复用 `components.md` 或项目已有组件；只写当前任务真实存在的状态。
5. 验收项写成“页面 / 状态 + 操作或条件 + 可观察结果”，供 `design-review.md` 直接核对。

材料不足时每次只问一个会改变产品方案的问题。材料充分，或用户要求“直接写”时，不重复确认；无法确认的内容标为“当前假设”。

## 完成前检查

- 信息来源、事实和假设是否分清？
- 页面、状态、组件、滚动和响应式是否能指导实现？
- 组件和 token 是否来自当前项目与 brand？
- 验收项是否可观察、可逐项检查？
- 是否误写了未要求的技术栈或 HTML？
